# Урок 3.1. API для основных сценариев

На интервью API выводим из действий пользователя и требований к результату. Для каждой операции назови, кто её вызывает, какие данные передаёт, что означает успех, какие ошибки ожидаем и что произойдёт при повторе. Начни с двух-трёх основных сценариев, затем добавь операции, без которых клиент не сможет завершить работу.

## От сценария к контракту

Продолжим пример с внутренним сервисом переговорных в одном офисе. Сотрудник находит комнату на заданный интервал, бронирует её и при необходимости отменяет свою бронь. Рассматриваем разовые бронирования. Смежные интервалы допустимы: бронь с 10:00 до 11:00 совместима с бронью с 11:00 до 12:00. Личность сотрудника берём из контекста аутентификации. Для просмотра и отмены конкретной брони проверяем, что она принадлежит сотруднику.

Из [контрольной по оценке нагрузки](../02-load-estimation/05-knowledge-check.md) берём отдельное представление доступности комнат. Оно обновляется после подтверждения брони или отмены. Цель свежести для поиска — 95% подтверждённых изменений видны в течение 5 секунд.

| Действие сотрудника | HTTP-операция | Успешный результат |
| --- | --- | --- |
| Найти свободные комнаты | `GET /rooms?from=…&to=…` | 200 и список комнат, свободных по данным поиска. Если свободных комнат нет, список пуст. |
| Создать бронь | `POST /bookings` | 201 и идентификатор подтверждённой брони. |
| Проверить свою бронь | `GET /bookings/{booking_id}` | 200 и текущее состояние брони из основного хранилища. |
| Отменить свою бронь | `POST /bookings/{booking_id}/cancel` | 200 и состояние cancelled. Историю бронирования сохраняем. |

Для создания клиент передаёт идентификатор комнаты и границы интервала. Для поиска и создания используем один формат времени с явным часовым поясом. Интервалы с концом раньше начала или равным началу отклоняем как некорректный запрос. Доступность комнаты проверяется при создании брони. Поиск помогает выбрать слот, а результат POST говорит, получилось ли его забронировать. [Семантика HTTP](https://www.rfc-editor.org/rfc/rfc9110.html)

Пример запроса на создание. Ключ в заголовке связывает повторную отправку с исходной операцией.

```http
POST /bookings HTTP/1.1
Host: booking.example.com
Content-Type: application/json
Idempotency-Key: booking-req-17

{"room_id":"r-42","from":"2026-12-01T10:00:00+03:00","to":"2026-12-01T11:00:00+03:00"}
```

## Когда отвечать об успехе

Допустим, два сотрудника увидели переговорную свободной и оба отправили POST на пересекающиеся интервалы. Запросу, который первым занял слот, сервис отвечает **201 Created** после фиксации подтверждённой брони. Конкурирующий запрос получает **409 Conflict**, потому что его интервал пересекается с подтверждённой бронью. В теле ошибки можно вернуть стабильный код room_unavailable, чтобы интерфейс мог предложить обновить результаты и выбрать другое время.

Сразу после ответа 201 поиск ещё может показать комнату свободной. Подтверждённая бронь уже хранится в основном хранилище, а данные поиска ещё обновляются. Для подтверждения своей брони сотрудник может открыть `GET /bookings/{booking_id}`. Гарантию отсутствия пересечений обеспечиваем при записи. Как сделать это при конкуренции, разберём в 4.2.

Если бы API лишь принимал заявку на будущее рассмотрение, можно было бы вернуть **202 Accepted** со ссылкой на состояние заявки. В этом контракте клиент ждёт отдельного подтверждения. Выбор между 201 и 202 определяется тем, что завершено к моменту ответа. [201 Created, 202 Accepted и 409 Conflict в RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html#section-15)

## Что произойдёт, если ответ потерялся

Сотрудник отправил `POST /bookings`. Сервис успел зафиксировать бронь, но соединение оборвалось до получения ответа. У клиента неопределённый результат. Если отправить независимую операцию, она встретит уже занятый слот. Чтобы восстановить результат исходной операции, клиент создаёт ключ идемпотентности до первой отправки и повторяет запрос с тем же ключом.

| Запрос | Какой результат обещает выбранный контракт |
| --- | --- |
| Та же операция от того же сотрудника, тот же ключ и те же данные после успешного создания | Возвращаем результат исходного создания с тем же booking_id. |
| Тот же ключ и изменённый интервал или комната | Отклоняем запрос с кодом idempotency_key_reused. |
| Другая операция на уже занятый интервал | Возвращаем 409 с кодом room_unavailable. |

В контракте фиксируем, что ключ уникален в рамках сотрудника и операции создания, как долго его помним и что возвращаем в случае повтора. В нашем примере повтор успешной операции возвращает исходный ответ 201 с тем же идентификатором. Для текущего состояния есть отдельный GET. Проверка ключа и защита слота отвечают за разные гарантии. Как хранить ключ и результат вместе с бронью, разберём в уроке о транзакциях. [Пример ключей идемпотентности в Stripe](https://docs.stripe.com/api/idempotent_requests)

Отмена в нашем API тоже идемпотентна по бизнес-эффекту. Если сотрудник повторил отмену уже отменённой собственной брони, возвращаем cancelled и сохраняем одно изменение состояния. При каждом обращении проверяем право на эту бронь. Если бронь чужая, выбранный контракт возвращает 404, как и для неизвестного ID.

## Как рассказать об API на интервью

Скажи, чем заканчивается основной сценарий, затем покажи запросы на чтение и запись. У записи проговори момент подтверждения, одно ожидаемое состояние конфликта и поведение после таймаута. Если продукт требует асинхронного обновления поиска, укажи, где клиент увидит подтверждённый результат и когда он появится в поиске. Из этих контрактов в уроке 3.2 выведем модель данных и запросы к ней. Путь запроса через компоненты системы и место API Gateway разберём в 3.3.
