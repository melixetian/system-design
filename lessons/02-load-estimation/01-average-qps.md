# Урок 01. От числа пользователей к среднему QPS

QPS (queries per second) показывает, сколько запросов в секунду поступает на выбранный компонент. Для HTTP также говорят RPS (requests per second). Чтобы оценить среднюю нагрузку, сначала назови участок системы и операцию, затем переведи объём работы за период в количество операций в секунду.

## Какие числа запросить на интервью

Начни с действий, которые нагружают систему. Сколько покупателей за день открывает отслеживание? Сколько раз в среднем каждый из них открывает страницу? Сколько HTTP-запросов делает приложение при одном открытии? Если известен только общий DAU (число активных пользователей за день), уточни, какая доля пользуется отслеживанием. Если интервьюер оставляет числа за тобой, обозначь их как допущения.

## Пример с отслеживанием заказов

Браузер ходит в публичный API магазина, а backend магазина читает данные во внутреннем сервисе отслеживания. Для оценки предположим, что одно открытие страницы вызывает один публичный GET, за которым следует один внутренний GET. Данные магазина и перевозчика приходят отдельным потоком.

| Поток | Оценка за сутки | Средняя нагрузка за 24 часа |
| --- | --- | --- |
| Чтение в сервисе отслеживания | 120 000 покупателей × 3 открытия × 1 запрос = 360 000 запросов | 360 000 / 86 400 ≈ 4,17 запроса/с |
| Входящие обновления | 40 000 новых заказов × 4 события на заказ ≈ 160 000 событий | 160 000 / 86 400 ≈ 1,85 события/с |

Число событий оцениваем в стабильном режиме, предполагая примерно одинаковый объём заказов в соседние дни. Например, сегодняшние вручения могут относиться ко вчерашним заказам. Если известно, сколько событий источники реально присылают за день, можно взять это число напрямую.

## Считаем нагрузку на нужном участке

В примере публичный API и сервис отслеживания получают по 4,17 запроса чтения в секунду. Если оцениваем только внутренний сервис, в расчёт берём его 4,17 запроса/с. Если backend объединяет статус и историю в одном ответе для браузера, но читает их двумя внутренними вызовами, внутренний поток при том же числе открытий вырастет до 8,33 запроса/с.

Для записи указывай единицу явно. При отправке по одному событию в HTTP-запросе 1,85 события/с дают 1,85 HTTP-запроса/с. При пакетной отправке по 10 событий получится около 0,185 HTTP-запроса/с, а обработчик по-прежнему получит 1,85 события/с. Число записей в базе оценивается отдельно по тому, сколько операций вызывает одно событие.

Среднее за сутки показывает порядок нагрузки. Для проверки пропускной способности и задержек в часы пик понадобится распределение трафика по времени. Этим займёмся в следующем уроке.

## Формулы для расчёта

| Величина | Как посчитать |
| --- | --- |
| Чтения на выбранном API за сутки | Покупатели, которые пользуются отслеживанием × открытия на покупателя × вызовы выбранного API на открытие |
| События за сутки | Новые заказы × среднее число событий на заказ, если поток заказов стабилен |
| Средняя скорость за сутки | Суточный объём ÷ 86 400 секунд |
| Средний HTTP RPS для пакетной отправки | События в секунду ÷ среднее число событий в HTTP-пакете |

Проверь расчёт на одном открытии страницы. Если браузер отправляет один запрос, а backend отдельно запрашивает статус и историю, одно открытие даёт один запрос на публичном API и два на внутреннем. Сумма по двум API пригодится, если оцениваешь общий трафик по всей цепочке.

## Упражнение

За сутки 180 000 покупателей открывают страницу отслеживания в среднем дважды. На каждое открытие backend делает два внутренних запроса — за статусом и за историей. Каждый день подтверждается 60 000 заказов, и на один заказ приходится в среднем четыре события. Считаем, что объём заказов примерно одинаков изо дня в день.

1. Каков средний QPS чтения на сервисе отслеживания?
2. Сколько событий в секунду он получает в среднем?
3. Если события присылают пакетами ровно по 10, сколько HTTP-запросов на приём событий поступает в среднем за секунду? Что поменяется для обработчика событий?

<details>
<summary>Разбор упражнения</summary>

1. Покупатели открывают страницу 180 000 × 2 = 360 000 раз за сутки. На каждое открытие два внутренних вызова, поэтому сервис отслеживания получает 720 000 чтений в сутки. Это **720 000 ÷ 86 400 ≈ 8,33 RPS**. Если браузер делает один запрос на открытие, на публичном API получается 360 000 ÷ 86 400 ≈ 4,17 RPS.
2. 60 000 × 4 = 240 000 событий в сутки, то есть **240 000 ÷ 86 400 ≈ 2,78 события/с**.
3. Пакетами по 10 получаем 24 000 запросов в сутки, или **около 0,278 HTTP-запроса/с**. Средняя входящая нагрузка обработчика остаётся 2,78 события/с. Дробную скорость удобно выразить за более длинный интервал. 0,278 запроса/с — это около 17 запросов в минуту в среднем за сутки. Реальный интервал между пакетами зависит от отправителя.

</details>
